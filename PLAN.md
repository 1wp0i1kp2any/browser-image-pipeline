# План и чеклист усиления `browser-image-pipeline`

**База:** v0.2.0 (`workspace-01a15197…zip`, архив D).  
**Статус документа:** фазы 0–1 выполнены в `v0.2.1` (заход 1), фаза 2 — в `v0.3.0` (заход 2), фаза 3 — в `v0.4.0` (заход 3), фазы 4–5 выполнены одним заходом 4 в `v0.5.0`; честно оставленные хвосты закрыты отдельным заходом в `v0.6.0`.  
**Источники:** мой сравнительный обзор четырёх архивов и независимый аудит `lib-images-review.md`.

## Краткое решение

Я бы не переписывал библиотеку и не заменял её ядро чужим. Основа D — конвейер,
реестр кодеков и поиск по фиксированным плоскостям с повторным поиском качества
внутри каждой плоскости — сохраняется. Усиление делается в таком порядке:

1. **Сначала исправить подтверждённую некорректность пикселей и границ поиска.**
2. **Затем сделать fit предсказуемым по ресурсам:** capabilities, бюджет,
   дедлайн, явная монотонность.
3. **Потом добавить расширяемость**, не ломая модель плоскостей: дескрипторы,
   стратегии как функции, изолированный реестр, state-collector.
4. **Оптимизации и донорские идеи включать только после воспроизводимых замеров**
   и тестов на равенство результата.

Новые форматы, новые пресеты и ещё один «умный» алгоритм до завершения первых двух
этапов не добавлять.

## Что независимый аудит изменил в моих прежних выводах

Независимый отчёт оказался полезнее моего обзора в части adversarial-проверок:
он нашёл конкретные дефекты D, которые я пропустил, потому что в основном
сравнивал архитектуру и штатные тесты. По текущему коду D я проверил механизмы
всех четырёх дефектов — они действительно присутствуют.

| Моя прежняя идея | Пересмотренное решение |
|---|---|
| Перенести обобщённые измерения B | Движок B не переносить. Брать только идею дескрипторов, но категориальные измерения перечислять плоскостями, а не искать по ним бинарно |
| Перенести `adaptive`/guard из A | Не переносить спуск A и `guard:'cheap'`: независимый аудит воспроизвёл деградацию относительно owner-loop. Допустима только новая стратегия **внутри quality-плоскости**, если она доказуемо возвращает ту же точку |
| Взять лёгкий квантователь C | Понизить приоритет и не портировать код как есть: аудит указал перепутанные диагональные веса Floyd–Steinberg и дефектный кэш. Возможна только независимая реализация идеи с эталонными тестами |
| Взять PNG-оптимизатор C | Код не портировать. Идея допустима только после сохранения цветовых/метаданных чанков, политики only-if-smaller и побитовой проверки пикселей |
| Добавить SizeModel | Не добавлять ради архитектуры. Сначала benchmark-корпус и порог пользы; модель может только выбирать следующую пробу внутри вилки и не имеет права менять результат |
| Считать главным недостатком D закрытость fit | Это важно, но теперь это **P2**. P0 — area, альфа bilinear, границы quality и nearest-cache в самой D |

## Неприкосновенные ограничения

Перед каждой фазой проверять, что не нарушено ни одно условие:

- [ ] Утверждённый публичный контракт не меняется; расширения только аддитивные.
- [ ] Предикат `fits` по-прежнему получает именно `Blob`.
- [ ] `fit` возвращает `null` только когда пространство поиска действительно исчерпано;
      незавершённый поиск из-за бюджета нельзя маскировать под доказанный no-fit.
- [ ] Ускоренные стратегии возвращают ту же точку, что owner-loop, при явно
      документированных предпосылках монотонности.
- [ ] Категориальные параметры не считаются монотонными без отдельного доказательства.
- [ ] Статический импорт ядра не тянет кодеки, image-q и wasm; тяжёлое остаётся ленивым.
- [ ] Нет двойного lossy-перекодирования; оптимизаторы — только lossless.
- [ ] Новых тяжёлых runtime-зависимостей нет.
- [ ] Вне браузера без decoder-шва — честная ошибка, а не молчаливый неверный результат.
- [ ] TypeScript strict; `any` в публичном API нет.
- [ ] Документация и комментарии — по-русски, идентификаторы — по-английски.

числовой профиль кэша палитр, abort-точки метрик и большой stress-корпус —
фаза 5. Кэш палитр уже ограничен двумя квантованными кадрами.

## Фаза 3. Расширяемость поверх модели плоскостей (`0.4.0`)

### 3.1. Сначала внутренний рефакторинг дескрипторов

- [x] Ввести внутренний дескриптор измерения плоскости с явным видом:
      `fixed`, `categorical`, `frame-transform`; quality оставить особой внутренней осью.
- [x] Перевести colors/channel/subsampling/variants на дескрипторы без изменения
      публичного API и порядка перебора.
- [x] Golden-тесты обязаны зафиксировать полный порядок плоскостей для комбинаций
      форматов, палитры, каналов, субсемплинга и variants.
- [x] Singleton-дескриптор превращается в `fixed` и применяется всегда.
- [x] Конфликты ключей опций между измерениями отклонять до первого энкода.

### 3.2. Публичные измерения — только после внутреннего этапа

- [x] Спроектировать аддитивные named categorical dimensions как развитие `variants`:
      пользователь задаёт независимые наборы опций, движок перечисляет плоскости.
- [x] В `FitParams` аддитивно возвращать выбранные значения именованных измерений.
- [x] Не обещать монотонность пользовательских опций и не применять к ним binary/secant.
- [x] Числовую пользовательскую ось разрешать только отдельным дизайном: явная
      декларация монотонности, функция применения, лестница и equivalence-тесты.
- [x] Если публичные dimensions не дают выигрыша по сравнению с существующими
      `variants`, остановиться на внутреннем рефакторинге и не расширять API ради симметрии с B.

### 3.3. Пользовательские стратегии качества

- [x] Разрешить передавать стратегию функцией/объектом в `FitOptions` в дополнение
      к встроенным именам; глобальный реестр добавлять только при реальном сценарии.
- [x] Контракт стратегии ограничить одной плоскостью и одной quality-лестницей:
      она не управляет форматами/плоскостями и не может сломать общий порядок жертв.
- [x] Передавать стратегии контекст пробы, сигнал и бюджет, но не Blob-предикат напрямую.
- [x] Дать тестовый harness для авторов стратегий: равенство owner-loop на синтетических
      монотонных кривых и запрет проб вне сетки.
- [x] `adaptive` из A не копировать; любая новая эвристика обязана сужать вилку и
      возвращать ту же границу.

### 3.4. Изолированный реестр кодеков

- [x] Выделить фабрику реестра (`createEncoderRegistry`), а существующие глобальные
      функции оставить обёрткой над default-реестром.
- [x] Добавить аддитивный `ImageOptions.registry`; `PipelineImpl` получает реестр
      через конструктор, а не импортирует глобальный Map напрямую.
- [x] Проверить два параллельных `image()` с разными реестрами и одинаковым MIME:
      регистрации не должны протекать друг в друга.
- [x] Проверить повторный вызов после неудачной загрузки ленивого кодека: rejected
      import/init не должен навсегда отравлять реестр, если это контролирует наша обёртка.
- [x] Отдельной задачей оценить subpath без автоподключения встроенных кодеков для
      DI-потребителей; не менять текущую точку входа и `sideEffects` без consumer-теста.

### 3.5. State-collector отдельным модулем

- [x] Сделать необязательный collector поверх существующего `options.state`:
      `listener`, `subscribe`, `getSnapshot`, текущий этап, attempts, timings, warnings.
- [x] Исключения каждого подписчика изолировать; сбой UI не должен ронять обработку
      (базовый emit уже защищён, collector обязан сохранить это свойство).
- [x] Вынести collector в отдельный export/subpath, чтобы ядро не росло для тех,
      кому нужен только callback.
- [x] Snapshot не должен отдавать мутабельные внутренние массивы попыток наружу.
- [x] Не добавлять зависимость от React или иного UI-фреймворка.

**Gate `0.4.0`:** старые примеры из README компилируются без изменений; порядок

**Факт захода 3 (`v0.4.0`):** gate пройден — strict typecheck, 113/113 тестов,
build/sizes/bench/demo build, ESM/CJS/DTS-проверка subpath `./state` и
`./testing`, браузерный smoke зелёные; bench и demo дали те же точки и пробы,

harness, изолированные реестры и отдельный state-collector. Числовая
пользовательская ось сознательно не добавлена: она допустима только
отдельным дизайном с явной монотонностью. Для legacy `variants` сохранён
исторический документированный приоритет нормированных измерений, а новые

реестр уже пуст и не загрязняется default-регистрациями, а вторая точка
входа требует отдельного consumer-сценария и проверки `sideEffects`.

## Решения, которые стоит утвердить перед фазами 2–3

1. Исчерпание бюджета по умолчанию — `FitBudgetExhaustedError` (рекомендация) или

   и вынести наружу только после проверки на встроенных кодеках?
3. Нужны ли именованные custom dimensions при уже существующих `variants`, или

4. Какой браузерный минимум заявляем для 1.0: только Chromium/Firefox с фактическими
   прогонами или также Safari/WebKit с отдельной матрицей ограничений?
5. Допустим ли отдельный subpath без авторегистрации встроенных кодеков для DI,
   или одна точка входа важнее изоляции?
